# Tasks


## 1. Exception Handling in Threads

In modern .NET, the framework completely changed how this works by moving away from raw Thread objects and wrapping everything in the Task parallel library.
1. The Modern Standard: `async` and `await`
When you use `await`, the compiler's state machine does the heavy lifting for you. It catches the exception on the background thread, transports it back to the calling thread, and rethrows it.

- How it works: You just use standard `try/catch` blocks.

- The behavior: If the background task throws an exception, the `await` keyword extracts the first exception and throws it natively.

Staff-Level Note: It preserves the original stack trace using `ExceptionDispatchInfo` under the hood, so you know exactly where the failure originated.

```csharp
try 
{
    await Task.Run(() => throw new InvalidOperationException("Failed on background thread."));
}
catch (InvalidOperationException ex) 
{
    // Caught safely on the calling thread
    Console.WriteLine(ex.Message); 
}
```

## 2. The Danger Zones (Architectural Traps)
**Trap 1:** `async void`
You should never write `async void MethodName()` unless it is a UI event handler (like a button click).

 - **Why:** An async void method cannot be awaited. If an exception is thrown inside it, it completely bypasses your `try/catch` blocks and goes straight to the Operating System, crashing your entire process instantly. Always use `async Task`.

**Trap 2: Fire-and-Forget Tasks (Unobserved Exceptions)**
If you start a `Task` but never `await` it, and it throws an exception, that exception is silently swallowed by the .NET framework when the Garbage Collector eventually cleans up the Task.

- **The Fix:** If you truly want a fire-and-forget background job, you must attach a continuation to log the error.

```csharp
// Fire and forget safely
Task.Run(() => DoWork())
    .ContinueWith(t => LogError(t.Exception), TaskContinuationOptions.OnlyOnFaulted);
```

### 3. Tasks vs ThreadPool
A `Thread Pool` is a low-level mechanism that manages a collection of pre-existing, reusable threads. A `Task` is a high-level abstraction (like a "promise") representing an asynchronous operation. Tasks do not replace thread pools; rather, they use the thread pool behind the scenes to execute work efficiently

**When to Use Which**
* **Use Tasks** for the vast majority of modern concurrent and asynchronous programming (e.g., handling I/O like web requests, or background calculations). They are cleaner, safer, and heavily integrated into modern language features like async/await.
* **Use Thread Pools** directly only if you need very specific low-level control over thread queuing or are working in environments that predate modern task libraries.

| Feature | Thread Pool | Task | 
| ----- | ----- | ----- | 
| **Level of Abstraction** | Low-level. Deals directly with creating, queuing, and assigning background threads. | High-level. Manages *what* needs to be done and *when* to check for results without micromanaging threads. | 
| **Return Values** | Cannot natively return results directly. Requires manual event signaling or shared memory state. | Easily returns results (e.g., `Task<T>`). | 
| **Chaining & Composition** | Difficult. To run one operation after another, you must manually hook callbacks or manage `WaitHandle` signals. | Built-in. You can seamlessly chain operations (e.g., continuations) using `await` and `ContinueWith`. | 
| **Error Handling** | Hard. Unhandled exceptions crash the process or get swallowed depending on the runtime. | Structured. Exceptions are bubbled up and easily caught in parent `try-catch` blocks. | 
| **Cancellation** | Requires you to manually poll a shared flag. | Native support using standard `CancellationToken` patterns.
