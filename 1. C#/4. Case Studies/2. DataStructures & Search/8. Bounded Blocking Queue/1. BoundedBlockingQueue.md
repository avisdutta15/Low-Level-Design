# Queue Is Not Thread-Safe

To understand why the standard `System.Collections.Generic.Queue<T>` in .NET is not thread-safe, we have to look at how it is built under the hood.

A standard `Queue<T>` does not use linked nodes; it uses a backing Array along with three internal integer variables to keep track of its state:

- `_head`: The index of the first item to dequeue.
- `_tail`: The index where the next item should be enqueued.
- `_size`: The total number of items currently in the queue.

When multiple threads access these variables at the exact same time without a lock, the internal state gets completely corrupted.

If you run this code, you expect the final queue count to be 100,000. But it will almost certainly be wrong, and it might even crash your program.

```csharp
using System.Threading;
using System.Collections.Generic;


public class Program
{
    public static void AddToQueue(Queue<int> Q)
    {
        for (int i = 1; i <= 1000; i++) 
        {
            Q.Enqueue(i);
        }
    }

    public static void Main(string[] args)
    {
        var queue = new Queue<int>();
        var threadList = new List<Thread>();
        Queue<int> q = new Queue<int>();

        // We spin up 100 threads each adding 1000 items
        for (int i = 0; i < 100; i++)
        {
            Thread t = new Thread(() => AddToQueue(q));
            t.Start();
            threadList.Add(t);
        }

        foreach(var t in threadList)
        {
            t.Join();
        }

        Console.WriteLine(q.Count);
    }
}
```

**The "Why": Breaking Down the Race Conditions**

Let's look at a simplified version of what Microsoft's `Enqueue` method actually does internally, and exactly how concurrent threads destroy it.

```csharp
// Simplified representation of .NET's Queue<T>.Enqueue()
public void Enqueue(T item) 
{
    // 1. Resize if full
    if (_size == _array.Length) {
        SetCapacity(_array.Length * 2); 
    }

    // 2. Insert the item
    _array[_tail] = item;           
    
    // 3. Move the tail and increment size
    _tail = (_tail + 1) % _array.Length;
    _size++;                        
}
```

Here are the three catastrophic race conditions that happen when Thread A and Thread B call Enqueue simultaneously:

**1. The Overwrite (Lost Data)**

 - Thread A reads `_tail` (let's say it is index 5).
 - Thread B reads `_tail` (it is also 5 because Thread A hasn't updated it yet).
 - Thread A writes its item to `_array[5]`.
 - Thread B writes its item to `_array[5]`, **overwriting Thread A's data**.
 - Both threads increment the tail. One item is permanently lost, but the size increases by two.

**2. The Stale Increment (_size++)**

The operation `_size++` is not a single CPU instruction. It is three steps: Read, Add, Write.
 - Thread A reads `_size` (e.g., 10).
 - Thread B reads `_size` (10).
 - Thread A adds 1 and writes 11.
 - Thread B adds 1 and writes 11.
 - Two items were added, but the queue size only increased by 1.

**3. The Resizing Crash (IndexOutOfRangeException)**

If the underlying array gets full, the Queue creates a new, larger array and copies the data over.
 - Thread A triggers `SetCapacity()`, which creates a new array.
 - While Thread A is copying data into the new array, Thread B tries to write to the old array, or worse, Thread B writes to an index that doesn't exist yet, throwing a fatal exception and crashing the application.


**The Fix**
If you need thread safety, wrap the standard queue in a `lock (queueLock) { queue.Enqueue(item); }`.

```csharp
private static object _lock = new object();

public static void AddToQueue(Queue<int> Q)
{
    for (int i = 1; i <= 1000; i++) 
    {
        lock (_lock)
        {
            Q.Enqueue(i);
        }
    }
}
```

# Concurrent Queue

```csharp
using System;
using System.Collections.Concurrent;
using System.Collections.Generic;
using System.Threading.Tasks;

public class Program
{
    // Notice: The lock object is completely gone!
    
    public static void AddToQueue(ConcurrentQueue<int> q)
    {
        // Fixed the loop to run exactly 1000 times (0 to 999)
        for (int i = 0; i < 1000; i++) 
        {
            // Thread-safe, lock-free enqueue
            q.Enqueue(i);
        }
    }

    public static async Task Main(string[] args)
    {
        var queue = new ConcurrentQueue<int>();
        var tasks = new List<Task>();

        // We queue up 100 tasks to the ThreadPool
        for (int i = 0; i < 100; i++)
        {
            // Task.Run is much lighter than 'new Thread()'
            tasks.Add(Task.Run(() => AddToQueue(queue)));
        }

        // Asynchronously wait for all tasks to complete without blocking the main thread
        await Task.WhenAll(tasks);

        Console.WriteLine($"Final Queue Count: {queue.Count}"); 
        // Output will perfectly be 100000
    }
}
```

**1. No OS Thread Overhead (The ThreadPool):** Your original code used `new Thread()`. Every time you do that, the OS has to allocate a 1MB memory stack and perform an expensive kernel transition. `Task.Run()` does not create new threads; it borrows existing, idle worker threads from the .NET ThreadPool. It is instantly faster and prevents memory exhaustion.

**2. No Context Switching (Lock-Free):** In your original code, if 100 threads hit that lock at the same time, 99 of them are put to sleep by the OS and then woken up one by one. This causes massive CPU context-switching overhead. The `ConcurrentQueue<T>` uses atomic CPU instructions (`Interlocked`), meaning threads just breeze right through without ever going to sleep.

**3. Non-Blocking Wait:** Your original code used `t.Join()`, which completely freezes the main calling thread until the workers are done. `await Task.WhenAll()` yields the main thread back to the application while it waits, which is critical for preventing UI freezes in desktop apps or thread-starvation in ASP.NET web servers.

# BoundedBlockingQueue - A Simple Implementation (Non Blocking)

```csharp
public class BoundedQueue
{
    # An array to hold the elements
    private int[] _buffer;
    private int _head;
    private int _tail;
    private int _capacity;
    private int _size;

    public BoundedQueue(int capacity)
    {
        _capacity = capacity;
        _buffer = new int[capacity];
        _head = 0;
        _tail = 0;
        _size = 0;
    }

    public int Capacity => _capacity;
    public int Count => _size;

    public void Enqueue(int item)
    {
        // Wait if the queue is full 
        if (_size == _capacity)
        {
            Console.WriteLine("Queue is full, producer waiting...");
            return;
        }

        // Insert the item and advance the tail pointer circularly
        _buffer[_tail] = item;
        _tail = (_tail + 1) % _capacity;
        _size++;        
    }

    public int Dequeue()
    {
        // Wait if the queue is empty (Blocks consumers)
        if (_size == 0)
        {
            Console.WriteLine("Queue is empty, producer waiting...");
        }

        // Read the item and advance the head pointer circularly
        var item = _buffer[_head];
        _head = (_head + 1) % _capacity;
        _size--;

        return item;        
    }
}

```

# BoundedBlockingQueue - A Blocking Thread-Safe Implementation (using Monitor)

```csharp
public class BoundedConcurrentQueue
{
    private int[] _buffer;
    private int _head;
    private int _tail;
    private int _capacity;
    private int _size;
    private readonly object _lock = new object();

    public BoundedConcurrentQueue(int capacity)
    {
        _capacity = capacity;
        _buffer = new int[capacity];
        _head = 0;
        _tail = 0;
        _size = 0;
    }

    public int Capacity => _capacity;
    public int Count => _size;

    public void Enqueue(int item)
    {
        lock (_lock)
        {
            // Wait if the queue is full (Throttles producers)
            if (_size == _capacity)
            {
                Monitor.Wait(_lock);
            }

            // Insert the item and advance the tail pointer circularly
            _buffer[_tail] = item;
            _tail = (_tail + 1) % _capacity;
            _size++;

            // Wake up waiting consumer threads
            Monitor.PulseAll(_lock);
        }
    }

    public int Dequeue()
    {
        lock (_lock)
        {
            // Wait if the queue is empty (Blocks consumers)
            if (_size == 0)
            {
                Monitor.Wait(_lock);
            }

            // Read the item and advance the head pointer circularly
            var item = _buffer[_head];
            _head = (_head + 1) % _capacity;
            _size--;

            // Wake up waiting producer threads
            Monitor.PulseAll(_lock);
            return item;
        }
    }
}
```
****

**The Bug: The "Stolen State" Problem**

When a thread wakes up from `Monitor.Wait`, it does not immediately execute. It simply gets moved back into the "ready" queue to wait for the `lock` to become available again.

Here is exactly how your if statement causes data corruption:

1. Your queue has a `capacity` of 1. It is `currently` full (`_size == 1`).

2. **Producer A** calls `Enqueue`. It sees `_size == 1`, enters the `if` block, and goes to sleep via `Monitor.Wait`.

3. **Producer B** calls `Enqueue`. It also sees `_size == 1`, enters the `if` block, and goes to sleep.

4. **Consumer A** calls `Dequeue`. It removes the item (`_size == 0`) and calls `Monitor.PulseAll()`.

5. **Producers A and B** both wake up and compete for the lock.

6. **Producer A** wins. It resumes execution exactly where it left off (right after the `Monitor.Wait` line). It enqueues its item, makes `_size == 1`, and releases the lock.

7. **Producer** B now gets the lock. Because it is using an if statement, it also resumes exactly where it left off. It does not check the size again. It blindly enqueues its item, overwriting **Producer A**'s data, and makes `_size == 2` (breaking your capacity limit).

**The Fix**
By changing the `if` to a `while`, you force the thread to re-verify the condition after it regains the lock. If another thread stole the slot while it was waking up, the `while` loop catches it and puts the thread safely back to sleep.


```csharp
using System.Threading;

public class BoundedConcurrentQueue
{
    private int[] _buffer;
    private int _head;
    private int _tail;
    private int _capacity;
    private int _size;
    private readonly object _lock = new object();

    public BoundedConcurrentQueue(int capacity)
    {
        _capacity = capacity;
        _buffer = new int[capacity];
        _head = 0;
        _tail = 0;
        _size = 0;
    }

    public int Capacity => _capacity;               // No need to use Volatile as it is set once in Ctor.
    public int Count => Volatile.Read(ref _size);   // It forces the CPU to fetch the most up-to-date 
                                                    // value from main memory, preventing the thread from reading 
                                                    // stale version of _size stuck in a CPU register.

    public void Enqueue(int item)
    {
        lock (_lock)
        {
            // FIX: Changed 'if' to 'while' to handle race conditions after waking up
            while (_size == _capacity)
            {
                Monitor.Wait(_lock);
            }

            _buffer[_tail] = item;
            _tail = (_tail + 1) % _capacity;
            _size++;

            Monitor.PulseAll(_lock);
        }
    }

    public int Dequeue()
    {
        lock (_lock)
        {
            // FIX: Changed 'if' to 'while' to handle race conditions after waking up
            while (_size == 0)
            {
                Monitor.Wait(_lock);
            }

            var item = _buffer[_head];
            _head = (_head + 1) % _capacity;
            _size--;

            Monitor.PulseAll(_lock);
            return item;
        }
    }
}
```
