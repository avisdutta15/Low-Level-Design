# 2. Open/Closed Principle (OCP)

## 1. What is it?

The Open/Closed Principle states that "Software entities (classes, modules, functions, etc.) should be open for extension, but closed for modification."

Open for extension: You should be able to add new features or behaviors to a class.

Closed for modification: You should be able to add these new features without changing the existing source code of that class.

## 2. Why is it needed?

* **Regression Bug Prevention**: Touching existing, tested, and working code is risky. By adding new features via new files/classes instead of editing old ones, you drastically reduce the chance of breaking existing functionality.

* **Easier Testing**: When you add a new feature, you only need to write unit tests for the new class you created. You don't have to rewrite or fix the unit tests for the old code.

* **Scalability**: As an application grows, switch statements and if-else chains can become hundreds of lines long. OCP prevents files from bloating into unmaintainable monsters.

## 3. Code Example in C# (The Violation)

A very common violation of OCP happens when developers use enums and switch or `if-else` statements to control business logic.

Look at this `DiscountCalculator`. It calculates discounts based on a customer's loyalty tier:

```csharp
public enum CustomerType
{
    Regular,
    Premium,
    VIP
}

public class DiscountCalculator
{
    public double CalculateTotal(CustomerType type, double amount)
    {
        // Violation: If we add a new CustomerType, we MUST modify this class!
        if (type == CustomerType.Regular)
        {
            return amount; 
        }
        else if (type == CustomerType.Premium)
        {
            return amount * 0.9; // 10% discount
        }
        else if (type == CustomerType.VIP)
        {
            return amount * 0.8; // 20% discount
        }
        
        return amount;
    }
}

```

**The Problem:** What happens when the marketing team wants to add an `"Employee"` discount tier or a `"SuperVIP"` tier? We are forced to open the `DiscountCalculator.cs` file and modify it by adding more else if conditions. The class is not closed for modification.

## 4. Why is it needed using C# (The Fix & C# Benefits)

In C#, the standard way to fix an OCP violation is by leveraging `Polymorphism` using `Interfaces` or `Abstract Classes`. This is often referred to as the `Strategy Pattern`.

Instead of having one class check the "type" and do the math, we let each customer type govern its own math.

### Approach A: Using an Interface

**Interfaces are perfect when you just need to enforce a contract with no shared logic.**

```csharp
using System;

// 1. Create an abstraction (The "Closed" part)
public interface IPriceRule
{
    double CalculateTotal(double amount);
}

// 2. Create concrete implementations (The "Open" part)
public class RegularCustomerRule : IPriceRule
{
    public double CalculateTotal(double amount) => amount;
}

public class VIPCustomerRule : IPriceRule
{
    public double CalculateTotal(double amount) => amount * 0.8;
}

// 3. The Calculator remains untouched no matter how many rules we add!
public class DiscountCalculator
{
    public double Calculate(IPriceRule pricingRule, double amount)
    {
        // It blindly trusts the interface. 
        return pricingRule.CalculateTotal(amount);
    }
}
```

### Approach B: Using an Abstract Class

Abstract classes are highly beneficial when the derived classes share common logic (like applying standard taxes) but still need to implement their own specific calculation logic.

```csharp
using System;

// 1. Create an abstract base class
public abstract class PriceRuleBase
{
    // Shared logic available to all derived classes
    protected double ApplyStandardTax(double amount)
    {
        return amount * 1.05; // Adds a 5% standard tax
    }

    // Abstract method forces derived classes to implement their own logic
    public abstract double CalculateTotal(double amount);
}

// 2. Concrete implementations inheriting the abstract class
public class EmployeeRule : PriceRuleBase
{
    public override double CalculateTotal(double amount)
    {
        double discountedAmount = amount * 0.5; // 50% employee discount
        return ApplyStandardTax(discountedAmount); // Reuse the shared logic!
    }
}

public class HolidaySpecialRule : PriceRuleBase
{
    public override double CalculateTotal(double amount)
    {
        double discountedAmount = amount - 20; // Flat $20 off
        return ApplyStandardTax(discountedAmount);
    }
}

// 3. The Calculator accepts the Abstract Class
public class AdvancedDiscountCalculator
{
    public double Calculate(PriceRuleBase pricingRule, double amount)
    {
        return pricingRule.CalculateTotal(amount);
    }
}
```

**C# Specific Benefits Here:** 
* **Zero Modification:** If marketing wants a new discount tomorrow, we simply create a new file NewRule.cs that implements IPriceRule or inherits `PriceRuleBase`. We do not have to touch the Calculator at all!

* **Dependency Injection (DI)**: C# heavily relies on DI. We can dynamically inject the correct rules at runtime making our C# applications incredibly modular.

## 5. Implementation Guidelines

* **The `"Switch/If"` Smell:** If you see a switch statement or an if-else chain checking the type or status of an object to execute different business logic, you are likely violating OCP.

* **Abstract the Volatile Parts:** Identify the parts of your application that change most frequently (e.g., pricing rules, export formats like PDF/CSV, notification types like SMS/Email) and hide them behind an interface or abstract class.

* **Interface vs Abstract Class:** Use an interface if the rules share no code and simply need a guaranteed method signature. Use an abstract class if the rules share common base logic or state that you don't want to duplicate in every single implementation.

* **Don't Pre-Optimize (YAGNI):** Don't make an interface for everything on day one. A common rule is "Fool me once, shame on you. Fool me twice, shame on me." If you have to modify an if statement once, just do it. If you have to modify it a second time for a third condition, refactor it to follow OCP.

* **Use the Strategy Pattern:** OCP and the Strategy Design Pattern go hand-in-hand. When in doubt, look up how to implement a Strategy Pattern in C#.
