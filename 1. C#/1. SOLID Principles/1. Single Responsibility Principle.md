# 1. Single Responsibility Principle (SRP)

## 1. What is it?

The Single Responsibility Principle states that **"A class should have one, and only one, reason to change."** In simpler terms, a class should only have one primary job or responsibility. If a class is doing multiple unrelated things, it violates this principle.

## 2. Why is it needed?

* **Maintainability:** Smaller, focused classes are easier to read and understand.

* **Testing:** It is much easier to write unit tests for a class that does one thing compared to a class that handles database calls, business logic, and UI updates.

* **Reduced Coupling:** If a class has multiple responsibilities, changing one part of the class might accidentally break another unrelated part (a regression bug).

* **Team Collaboration:** Different developers can work on different classes (e.g., one on logging, one on database access) without causing merge conflicts in a single massive file.

## 3. Code Example in C# (The Violation)

Here is a common real-world example of an SRP violation. This `UserService` class is doing way too much: it handles business logic, database operations, and email notifications.

```csharp
using System;
using System.IO;

public class UserService
{
    public void RegisterUser(string username, string email)
    {
        // Responsibility 1: Business Logic
        if (string.IsNullOrWhiteSpace(username) || string.IsNullOrWhiteSpace(email))
        {
            throw new ArgumentException("Invalid user data.");
        }

        // Responsibility 2: Database Operations / Persistence
        Console.WriteLine($"Saving user {username} to the database...");
        
        // Responsibility 3: Logging
        File.AppendAllText("log.txt", $"User {username} registered at {DateTime.Now}\n");

        // Responsibility 4: Notifications
        Console.WriteLine($"Sending welcome email to {email}...");
    }
}
```

**The Problem:** If we want to change how we log errors (e.g., log to an external service instead of a file), we have to modify the `UserService`. If we want to change our email provider, we *again* modify the `UserService`. It has too many reasons to change!

## 4. Why is it needed using C# (The Fix & C# Benefits)

In C#, we fix this by separating these responsibilities into distinct classes and connecting them using **Dependency Injection (DI)** and **Interfaces**. This is exactly how modern C# (.NET Core / .NET 5+) is designed to be written.

Here is the refactored, SRP-compliant C# code:

```csharp
using System;

// 1. Notification Responsibility
public interface IEmailService
{
    void SendEmail(string to, string message);
}

public class EmailService : IEmailService
{
    public void SendEmail(string to, string message)
    {
        Console.WriteLine($"Sending email to {to}: {message}");
    }
}

// 2. Logging Responsibility
public interface ILogger
{
    void LogInfo(string message);
}

public class FileLogger : ILogger
{
    public void LogInfo(string message)
    {
        // Cleanly encapsulated logging logic
        Console.WriteLine($"[LOG]: {message}"); 
    }
}

// 3. User Persistence Responsibility
public interface IUserRepository
{
    void Save(string username, string email);
}

public class UserRepository : IUserRepository
{
    public void Save(string username, string email)
    {
        Console.WriteLine($"Saving user {username} to database...");
    }
}

// 4. Business Logic Responsibility (Clean UserService)
public class UserService
{
    private readonly IUserRepository _userRepository;
    private readonly ILogger _logger;
    private readonly IEmailService _emailService;

    // C# Constructor Injection
    public UserService(IUserRepository userRepository, ILogger logger, IEmailService emailService)
    {
        _userRepository = userRepository;
        _logger = logger;
        _emailService = emailService;
    }

    public void RegisterUser(string username, string email)
    {
        if (string.IsNullOrWhiteSpace(username) || string.IsNullOrWhiteSpace(email))
        {
            throw new ArgumentException("Invalid user data.");
        }

        // The UserService now orchestrates the work, rather than doing everything itself.
        _userRepository.Save(username, email);
        _logger.LogInfo($"User {username} registered successfully.");
        _emailService.SendEmail(email, "Welcome to our platform!");
    }
}
```

**C# Specific Benefits Here:** By separating responsibilities, we can use C#'s `Microsoft.Extensions.DependencyInjection` to inject these services. We can now easily swap out `FileLogger` for an `AzureAppInsightsLogger` without ever touching the `UserService` code!

## 5. Implementation Guidelines

* **The "And" Rule:** If you try to describe what a class does and you use the word "and" (e.g., "This class saves the user *and* sends an email"), you are likely violating SRP.

* **Look at your `using` statements:** If a C# class has `using System.Data.SqlClient;`, `using System.Net.Mail;`, and `using System.IO;`, it's almost certainly doing too much.

* **Cohesion:** Group methods and properties that change together. If a class has a set of methods that only use half of the class's private fields, those methods probably belong in their own class.

* **Don't over-fragment:** Don't create a class for every single method. Group them by *responsibility* (e.g., `EmailService` can handle `SendPasswordReset`, `SendWelcomeEmail`, etc., because they all share the responsibility of emailing).
