# 3. Liskov Substitution Principle (LSP)

## 1. What is it?

**"Objects of a base class shall be replaceable with objects of its derived class without breaking the application."**

In simpler terms: If you have a base class and a child class, you should be able to swap out the base class for the child class anywhere in your code, and the program should still behave perfectly normally.


## 2. Why is it needed?

* **Predictability:** When a developer writes a function that accepts a base class (like `Employee`), they expect any child class (like `FullTimeEmployee` or `Contractor`) to honor the rules of `Employee`. If passing a `Contractor` makes the payroll calculation crash, the hierarchy is broken.

* **Avoiding Type Checking:** If you constantly have to write `if (obj is Contractor) { // do something else }` to prevent crashes, you are violating LSP and defeating the entire purpose of Polymorphism.

* **Interface Reliability:** It ensures that interfaces and base classes are actually trustworthy contracts.

## 3. Code Example in C# (The Violation)

The most common violation of LSP in C# is when a derived class throws a `NotImplementedException` or `NotSupportedException` for a method it inherited but can't logically perform.

Let's look at a classic "Employee Bonus" example:

```csharp
using System;
using System.Collections.Generic;

public abstract class Employee
{
    public string Name { get; set; }
    
    // The base class forces ALL employees to have a bonus calculation
    public abstract decimal CalculateBonus();
}

public class FullTimeEmployee : Employee
{
    public override decimal CalculateBonus()
    {
        return 1000m; // Full-time employees get a fixed bonus
    }
}

public class Contractor : Employee
{
    public override decimal CalculateBonus()
    {
        // Violation! Contractors do not get bonuses.
        // This completely breaks the expectation of the base class.
        throw new NotSupportedException("Contractors do not receive bonuses!");
    }
}

public class PayrollManager
{
    public void ProcessBonuses(List<Employee> employees)
    {
        foreach (var employee in employees)
        {
            // If a Contractor is in this list, the application CRASHES here!
            Console.WriteLine($"{employee.Name} gets a bonus of {employee.CalculateBonus()}");
        }
    }
}
```
**The Problem:** `Contractor` IS-A `Employee`, but it cannot be *substituted* for an `Employee` when bonuses are involved. The `PayrollManager` assumes all employees get bonuses. We violated the contract.

## 4. Why is it needed using C# (The Fix & C# Benefits)

To fix this in C#, we need to refactor our abstractions. Instead of forcing all employees to have a bonus calculation, we should create smaller, more accurate contracts using Interfaces.

Here is the refactored, LSP-compliant C# code:

```csharp
using System;
using System.Collections.Generic;

// 1. A pure base class that applies to ALL employees
public abstract class Employee
{
    public string Name { get; set; }
    public abstract decimal CalculatePay(); // All employees get paid!
}

// 2. A specific interface ONLY for employees eligible for bonuses
public interface IBonusEligible
{
    decimal CalculateBonus();
}

// 3. FullTimeEmployee IS an Employee, AND is eligible for a bonus
public class FullTimeEmployee : Employee, IBonusEligible
{
    public override decimal CalculatePay() => 5000m; // Base salary
    public decimal CalculateBonus() => 1000m;
}

// 4. Contractor IS an Employee, but CANNOT get a bonus. It doesn't implement IBonusEligible.
public class Contractor : Employee
{
    public override decimal CalculatePay() => 3000m; // Hourly pay
}

// 5. The Manager now explicitly asks for IBonusEligible. 
// It is impossible to accidentally pass a Contractor here!
public class PayrollManager
{
    public void ProcessBonuses(List<IBonusEligible> bonusEligibleEmployees)
    {
        foreach (var employee in bonusEligibleEmployees)
        {
            employee.CalculateBonus(); // 100% safe. No exceptions will be thrown.
        }
    }
}
```

**C# Specific Benefits Here:** 
* **Compile-Time Safety:** Because we separated the types, if you try to pass a Contractor into `PayrollManager.ProcessBonuses()`, the C# compiler will instantly throw a red squiggly error. You catch the bug while typing, rather than crashing in production.
* **Cleaner Interfaces:** By avoiding forced base-class inheritance, our code becomes much more modular and realistic to actual business rules.


## 5. Implementation Guidelines
* No new exceptions can be thrown by the subclass.
* Clients should not know which specific subtype they are calling.
* New derived classed just extend without replacing the functionality of old classes.
