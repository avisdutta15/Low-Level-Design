# Copy-On-Write (COW) Technique

## What is Copy-On-Write?

Copy-On-Write is a concurrency strategy where shared data is never mutated in place. Instead, when a modification is needed, the writer creates a new copy of the data with the change applied, then atomically swaps the reference from the old version to the new one. Readers always see a consistent snapshot — they either see the old version or the new version, never a half-written state.

The key insight: **reads require no synchronization at all**. Only writes pay the cost of copying and swapping.

### Core Principle

```
Thread A (reader):  reads reference → gets pointer to Version 1 → iterates safely
Thread B (writer):  reads reference → copies Version 1 → modifies copy → atomically swaps reference to Version 2
Thread A:           still iterating Version 1 (unaffected, GC keeps it alive)
Thread C (reader):  reads reference → gets pointer to Version 2 → sees updated data
```

No locks. No blocking. No `InvalidOperationException: Collection was modified`.

---

## Why Use Copy-On-Write?

| Scenario | COW Advantage |
|----------|---------------|
| Read-heavy workloads (event dispatch, caches, config) | Zero-cost reads, no lock contention |
| Iteration during modification | Readers iterate a stable snapshot |
| Lock-free requirement | No deadlocks, no priority inversion |
| Simple reasoning | Immutable snapshots are easy to reason about |

**Not ideal when:** Writes are very frequent or the data structure is very large (copying becomes expensive).

## Approach 1: Manual CAS Loop with `Interlocked.CompareExchange`

This is the fundamental building block. You implement the copy-on-write swap yourself using a compare-and-swap (CAS) primitive.

### How CAS Works

`Interlocked.CompareExchange(ref location, newValue, expectedValue)` does the following **atomically** (as a single CPU instruction):

1. Reads the current value at `location`
2. If it equals `expectedValue`, replaces it with `newValue`
3. Returns the value that was at `location` before the operation

If another thread modified `location` between your read and your CAS attempt, the comparison fails, and you know you need to retry.

### The CAS Loop Pattern

```
1. Read the current reference (snapshot)
2. Create a modified copy based on that snapshot
3. Attempt to swap: CompareExchange(ref field, newCopy, snapshot)
4. If swap succeeded → done
5. If swap failed (another thread beat us) → go to step 1
```

### Full Implementation

```csharp
public class CopyOnWriteList<T>
{
    // Volatile ensures all threads see the latest reference
    // (prevents CPU register caching of the pointer)
    private volatile List<T> _items = new List<T>();

    /// <summary>
    /// Reads are completely lock-free.
    /// Returns the current snapshot — safe to iterate even if another thread is writing.
    /// </summary>
    public List<T> GetSnapshot() => _items;

    /// <summary>
    /// Adds an item using a manual CAS loop.
    /// </summary>
    public void Add(T item)
    {
        // Spin until we succeed
        while (true)
        {
            // Step 1: Capture the current reference
            List<T> original = _items;

            // Step 2: Create a modified copy
            List<T> copy = new List<T>(original) { item };

            // Step 3: Atomically swap IF no one else changed it
            List<T> result = Interlocked.CompareExchange(ref _items, copy, original);

            // Step 4: Check if we won the race
            if (ReferenceEquals(result, original))
            {
                // Our swap succeeded — the reference now points to our copy
                return;
            }

            // Step 5: Someone else swapped between our read and our CAS.
            // `result` contains what _items actually was (the other thread's version).
            // We must retry: re-read, re-copy, re-attempt.
        }
    }

    /// <summary>
    /// Removes an item using the same CAS loop pattern.
    /// </summary>
    public bool Remove(T item)
    {
        while (true)
        {
            List<T> original = _items;

            // If item isn't present, nothing to do
            if (!original.Contains(item))
                return false;

            List<T> copy = new List<T>(original);
            copy.Remove(item);

            List<T> result = Interlocked.CompareExchange(ref _items, copy, original);

            if (ReferenceEquals(result, original))
                return true;

            // Retry — another thread modified the list
        }
    }

    /// <summary>
    /// Iteration is always safe — we're reading an immutable snapshot.
    /// </summary>
    public void ForEach(Action<T> action)
    {
        // Grab the reference once — even if _items changes after this line,
        // we iterate over the version we captured
        List<T> snapshot = _items;

        foreach (T item in snapshot)
        {
            action(item);
        }
    }
}
```

### Step-by-Step Execution Trace

```
Time 0: _items → [A, B, C]

Thread 1 (Add "D"):                    Thread 2 (Add "E"):
─────────────────────                  ─────────────────────
1. original = [A, B, C]               1. original = [A, B, C]
2. copy = [A, B, C, D]                2. copy = [A, B, C, E]
3. CAS(_items, copy, original)        3. CAS(_items, copy, original)
   → _items was [A,B,C] ✓               → _items is now [A,B,C,D] ✗
   → swap succeeds!                      → CAS fails (expected [A,B,C])
   → _items → [A, B, C, D]              → retry!

                                       1. original = [A, B, C, D]  (re-read)
                                       2. copy = [A, B, C, D, E]
                                       3. CAS(_items, copy, original)
                                          → _items was [A,B,C,D] ✓
                                          → swap succeeds!
                                          → _items → [A, B, C, D, E]
```

Both adds are preserved. No data loss. No locks.

### When CAS Retries Are a Problem (ABA Problem)

The CAS loop can theoretically suffer from the **ABA problem**: Thread 1 reads value A, Thread 2 changes it to B then back to A, Thread 1's CAS succeeds even though the data was modified. With reference types in .NET and GC, this is **not a practical concern** — if no one holds a reference to the old list, GC collects it and a new list at the same memory address is a different object. `ReferenceEquals` won't match unless it's truly the same object.

## Approach 2: `ImmutableInterlocked.Update`

Microsoft provides a higher-level abstraction in `System.Collections.Immutable` that encapsulates the CAS loop for you.

### How `ImmutableInterlocked.Update` Works Internally

```csharp
// Simplified version of what ImmutableInterlocked.Update does internally:
public static void Update<T>(ref T location, Func<T, T> transformer) 
    where T : class
{
    while (true)
    {
        T original = Volatile.Read(ref location);
        T updated = transformer(original);
        
        // If the transformation returned the same reference, no change needed
        if (ReferenceEquals(original, updated))
            return;
        
        T actual = Interlocked.CompareExchange(ref location, updated, original);
        
        if (ReferenceEquals(actual, original))
            return; // Success
        
        // Failed — another thread modified it. Retry with fresh state.
    }
}
```

It's exactly the CAS loop from Approach 1, but generalized. You provide a transformation function, and it handles the retry logic.

### Implementation Using `ImmutableList<T>`

```csharp
using System.Collections.Immutable;

public class CopyOnWriteObserverList
{
    private ImmutableList<IObserver> _observers = ImmutableList<IObserver>.Empty;

    public void Subscribe(IObserver observer)
    {
        // The lambda is the "transformation function"
        // It receives the current list and returns a new one with the observer added
        ImmutableInterlocked.Update(
            ref _observers,
            list => list.Contains(observer) ? list : list.Add(observer)
        );
    }

    public void Unsubscribe(IObserver observer)
    {
        ImmutableInterlocked.Update(
            ref _observers,
            list => list.Remove(observer)
        );
    }

    public void NotifyAll(string message)
    {
        // Reading _observers gives us an immutable snapshot
        // No lock, no copy — the reference itself IS the snapshot
        foreach (var observer in _observers)
        {
            observer.Update(message);
        }
    }
}
```

### Why `ImmutableList` Is Efficient for COW

`ImmutableList<T>` doesn't copy the entire list on every mutation. It uses a **balanced binary tree** (AVL tree) internally with **structural sharing**:

```
Original list: [A, B, C, D, E]

Internal tree:
        C
       / \
      B   D
     /     \
    A       E

After Add("F"):
        C                    (shared with original)
       / \
      B   D*                 (new node)
     /   / \
    A   E   F               (E shared, F new)
```

Only the path from the root to the modified node is copied (O(log n) nodes). The rest of the tree is shared between old and new versions. This means:
- `Add` / `Remove` = O(log n) time and space (not O(n))
- Old readers still iterate the original tree safely
- GC reclaims unreachable nodes when all readers finish

### `ImmutableInterlocked.Update` vs Manual CAS: Comparison

| Aspect | Manual CAS with `List<T>` | `ImmutableInterlocked.Update` |
|--------|---------------------------|-------------------------------|
| Copy cost per write | O(n) — entire list copied | O(log n) — structural sharing |
| Memory per write | Full new list allocated | Only changed path nodes |
| Retry cost | Must re-copy entire list | Only re-apply transformation |
| Code complexity | Manual loop + error prone | One-liner |
| Read cost | Free (reference read) | Free (reference read) |
| Contains check | O(n) on `List<T>` | O(n) on `ImmutableList<T>` |

## Approach 3: `ImmutableInterlocked` with Other Collections

### Using `ImmutableHashSet<T>` (O(1) Contains)

```csharp
using System.Collections.Immutable;

public class UniqueObserverSet
{
    private ImmutableHashSet<IObserver> _observers = ImmutableHashSet<IObserver>.Empty;

    public void Subscribe(IObserver observer)
    {
        // HashSet inherently prevents duplicates — no manual Contains check needed
        ImmutableInterlocked.Update(ref _observers, set => set.Add(observer));
    }

    public void Unsubscribe(IObserver observer)
    {
        ImmutableInterlocked.Update(ref _observers, set => set.Remove(observer));
    }

    public void NotifyAll(string message)
    {
        foreach (var observer in _observers)
        {
            observer.Update(message);
        }
    }
}
```

Better than `ImmutableList` when you need uniqueness — `Add` on a set is O(log n) and automatically deduplicates.

### Using `ImmutableDictionary<TKey, TValue>` (Keyed Lookup)

```csharp
using System.Collections.Immutable;

public class NamedObserverRegistry
{
    private ImmutableDictionary<string, IObserver> _observers = 
        ImmutableDictionary<string, IObserver>.Empty;

    public void Register(string name, IObserver observer)
    {
        ImmutableInterlocked.Update(ref _observers, dict => dict.SetItem(name, observer));
    }

    public void Deregister(string name)
    {
        ImmutableInterlocked.Update(ref _observers, dict => dict.Remove(name));
    }

    public void NotifyAll(string message)
    {
        foreach (var kvp in _observers)
        {
            kvp.Value.Update(message);
        }
    }

    public IObserver? GetObserver(string name)
    {
        // Lock-free lookup — O(log n) on the hash trie
        return _observers.TryGetValue(name, out var observer) ? observer : null;
    }
}
```

## Approach 4: Manual COW with `volatile` + Array Swap

For maximum performance when you need the absolute lowest overhead and are willing to trade flexibility:

```csharp
public class UltraFastCowObservers
{
    // Arrays are fixed-size — truly immutable once created
    private volatile IObserver[] _observers = Array.Empty<IObserver>();

    public void Subscribe(IObserver observer)
    {
        while (true)
        {
            IObserver[] original = _observers;

            // Check for duplicates
            if (Array.IndexOf(original, observer) >= 0)
                return;

            // Create new array with one extra slot
            IObserver[] updated = new IObserver[original.Length + 1];
            Array.Copy(original, updated, original.Length);
            updated[original.Length] = observer;

            if (ReferenceEquals(
                Interlocked.CompareExchange(ref _observers, updated, original),
                original))
            {
                return;
            }
        }
    }

    public void Unsubscribe(IObserver observer)
    {
        while (true)
        {
            IObserver[] original = _observers;
            int index = Array.IndexOf(original, observer);

            if (index < 0)
                return;

            IObserver[] updated;
            if (original.Length == 1)
            {
                updated = Array.Empty<IObserver>();
            }
            else
            {
                updated = new IObserver[original.Length - 1];
                Array.Copy(original, 0, updated, 0, index);
                Array.Copy(original, index + 1, updated, index, original.Length - index - 1);
            }

            if (ReferenceEquals(
                Interlocked.CompareExchange(ref _observers, updated, original),
                original))
            {
                return;
            }
        }
    }

    public void NotifyAll(string message)
    {
        // Single volatile read — then pure array iteration (CPU cache friendly)
        IObserver[] snapshot = _observers;
        for (int i = 0; i < snapshot.Length; i++)
        {
            snapshot[i].Update(message);
        }
    }
}
```

**Why this can be faster than `ImmutableList`:**
- Arrays have better CPU cache locality (contiguous memory) vs tree nodes (pointer chasing)
- No tree rebalancing overhead
- `for` loop over array is optimized by JIT (bounds-check elimination)
- Zero allocations on the read path

**Trade-off:** O(n) copy cost on every write. Only use when the collection is small (< 100 items) and writes are rare.

## Internal Mechanics: `volatile` vs `Interlocked` vs `lock`

### Why `volatile` Alone Isn't Enough for Writes

```csharp
private volatile List<T> _items;

// BROKEN — NOT ATOMIC:
_items = new List<T>(_items) { newItem };
// This is: read _items → create new list → assign _items
// Another thread can modify _items between the read and assign!
```

`volatile` only guarantees:
1. The CPU won't cache the field in a register (always reads from memory)
2. Reads/writes won't be reordered past the volatile access

It does NOT make read-modify-write atomic. That's why we need CAS.

### Why `Interlocked.CompareExchange` Is Atomic

On x86/x64, `Interlocked.CompareExchange` compiles to the `CMPXCHG` CPU instruction with a `LOCK` prefix. This:
1. Locks the cache line (not a software lock — a hardware bus lock or cache lock)
2. Performs compare + exchange in one indivisible operation
3. Provides full memory barrier (no reordering across it)

No other core can observe the memory location in a half-written state.

### Memory Ordering Guarantees

```
Thread 1:                           Thread 2:
writes to copy[0], copy[1]...       
Interlocked.CompareExchange         reads _items reference
(full memory barrier)               (volatile read = acquire fence)
                                    reads copy[0], copy[1]...
```

The memory barrier in `CompareExchange` ensures all writes to the new copy are visible to other threads before the reference becomes visible. Without this, Thread 2 might see the new reference but read stale/uninitialized array elements due to CPU store buffer reordering.

## Performance Characteristics Summary

| Operation | Manual CAS (Array) | `ImmutableList<T>` | `ImmutableHashSet<T>` |
|-----------|--------------------|--------------------|----------------------|
| Read/Iterate | O(n), cache-friendly | O(n), pointer-chasing | O(n), pointer-chasing |
| Add | O(n) copy | O(log n) | O(log n) |
| Remove | O(n) copy | O(log n) | O(log n) |
| Contains | O(n) | O(n) | O(log n) |
| Memory per mutation | Full copy | Shared path | Shared path |
| Best for | Small, read-hot collections | Medium collections | Uniqueness required |

## Real-World Example: Thread-Safe Event Bus

Putting it all together in a production-style implementation:

```csharp
using System.Collections.Immutable;

public class EventBus
{
    // Each event type has its own observer list — independent COW per type
    private ImmutableDictionary<Type, ImmutableList<Delegate>> _handlers =
        ImmutableDictionary<Type, ImmutableList<Delegate>>.Empty;

    public void Subscribe<TEvent>(Action<TEvent> handler)
    {
        ImmutableInterlocked.Update(ref _handlers, dict =>
        {
            var key = typeof(TEvent);
            var existing = dict.GetValueOrDefault(key, ImmutableList<Delegate>.Empty);
            return dict.SetItem(key, existing.Add(handler));
        });
    }

    public void Unsubscribe<TEvent>(Action<TEvent> handler)
    {
        ImmutableInterlocked.Update(ref _handlers, dict =>
        {
            var key = typeof(TEvent);
            if (!dict.TryGetValue(key, out var existing))
                return dict;
            var updated = existing.Remove(handler);
            return updated.IsEmpty ? dict.Remove(key) : dict.SetItem(key, updated);
        });
    }

    public void Publish<TEvent>(TEvent evt)
    {
        // Lock-free snapshot read of the entire handler dictionary
        var handlers = _handlers;

        if (handlers.TryGetValue(typeof(TEvent), out var list))
        {
            foreach (var handler in list)
            {
                ((Action<TEvent>)handler)(evt);
            }
        }
    }
}

// Usage:
var bus = new EventBus();

bus.Subscribe<OrderPlaced>(e => Console.WriteLine($"Order {e.OrderId} placed"));
bus.Subscribe<OrderPlaced>(e => SendEmail(e));

// Safe to publish from any thread — no locks on the hot path
bus.Publish(new OrderPlaced { OrderId = 42 });
```

## When NOT to Use Copy-On-Write

1. **Write-heavy workloads** — If writes happen more often than reads, the constant copying/swapping is wasteful. Use a `ConcurrentDictionary` or lock-based approach instead.

2. **Large collections with frequent mutations** — Copying a 10,000-element array on every add is expensive. Structural sharing (`ImmutableList`) helps but still has O(log n) overhead per write.

3. **Strict ordering requirements** — COW provides eventual consistency. If you need "Thread A's unsubscribe must take effect before Thread B's next notification," you need stronger synchronization.

4. **Memory-constrained environments** — Old versions of the collection live in memory until GC collects them (when all readers finish). Under high write rates, many generations can accumulate temporarily.

---

## Summary

| Approach | Complexity | Best Use Case |
|----------|-----------|---------------|
| Manual CAS + `List<T>` copy | Medium | Learning, small collections |
| Manual CAS + Array | Medium-High | Ultra-low-latency, small fixed collections |
| `ImmutableInterlocked.Update` + `ImmutableList<T>` | Low | General-purpose, most observer patterns |
| `ImmutableInterlocked.Update` + `ImmutableHashSet<T>` | Low | When uniqueness/fast lookup matters |
| `ImmutableInterlocked.Update` + `ImmutableDictionary` | Low | Keyed/categorized collections |

The golden rule: **if your collection is read 100x more than it's written, Copy-On-Write is almost certainly the right choice.**
